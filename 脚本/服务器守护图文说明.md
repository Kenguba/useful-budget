# 服务器守护图文说明

配套脚本：[install-server-guards.sh](./install-server-guards.sh)

自有服务器的三层守护：两层装在服务器里、一层在 Muse 侧。换新服务器时，服务器内的两层跑一键脚本一次装好，第三层由 Muse 照本说明重建。

## 三层总览

| 层 | 名字 | 在哪 | 干什么 |
|---|---|---|---|
| 1 | 流量守卫 traffic-guard | 服务器内 | 每 5 分钟统计出向流量，超阈值先停 VPN、再封对外，防流量超额扣费 |
| 2 | fail2ban | 服务器内 | 盯 SSH 登录失败，爆破 IP 自动封禁 |
| 3 | 每日检测看门狗 | Muse 侧 cron | 每天巡检一遍服务器，只报异常不处置（主机密钥自动还原除外） |

## 部署前逐项检测（先查有没有，再动手）

部署前先逐项检测每一件在不在、状态对不对，缺什么补什么，不对的先停手核对。脚本自带只读检测：

```bash
GUARD_CHECK_DOMAINS="word.xxxxx.asia eg.xxxxx.asia" bash install-server-guards.sh --preflight
```

逐项口径：

- 服务器内：流量守卫的程序、service、timer（已启用且运行中）、状态文件；fail2ban 的程序、jail 配置、运行状态
- 域名侧：本机承载的每个域名逐个查——DNS 记录在不在、指向对不对、Cloudflare 代理是橙云（开）还是灰云（关）
- Muse 侧：每日检测看门狗的 cron 在不在、巡检目标是不是这台机、已知 IP 与主机密钥指纹清单是否已换成新机的

云状态的查法：脚本用公共解析推断——解析直达本机公网 IP = 灰云，解析到 Cloudflare 地址段或隧道记录 = 橙云。推断只作旁证，最终以 Cloudflare 后台该记录的 proxied 开关为准；推断与预期对不上，先去后台核对再部署。

现行新加坡机承载的域名与定版状态：

| 域名 | 定版状态 | 说明 |
|---|---|---|
| word 子域名 | 橙云 + Tunnel | 隧道记录必须开代理，关掉当场打不开，不动 |
| eg 子域名 | 灰云直连 | 例子站故意直连源站 IP，保持灰云 |

其余子域名走 GitHub Pages + Worker、不经这台服务器，不在本脚本的部署与检测范围内，动它们时按各自规范逐项检测。

## 一键安装（第 1、2 层）

在新服务器上（Ubuntu）：

```bash
sudo bash install-server-guards.sh
```

正式安装时脚本会先自动跑一遍上面的逐项检测再动手；装完脚本会自检并打印两层的当前状态。可重复运行（幂等），但重跑会重启 fail2ban、清空它当前的封禁名单，名单会随攻击者重试很快重新形成。

可选参数（环境变量，不给就用现行新加坡机的定版值）：

```bash
sudo GUARD_T1_GB=780 GUARD_T2_GB=790 GUARD_ANCHOR_DAY=8 GUARD_IFACE=eth0 bash install-server-guards.sh
```

- `GUARD_T1_GB` / `GUARD_T2_GB`：一级 / 二级流量阈值（GB，十进制），按新机套餐总量留余量定；现行机套餐 800GB，定 780 / 790
- `GUARD_ANCHOR_DAY`：流量周期起始日，现行机是购买日 8 号
- `GUARD_IFACE`：统计的网卡，现行机 eth0
- `GUARD_OWN_IP`：fail2ban 白名单里的服务器自身公网 IP，不给则脚本自动探测，探测不到就只留本机回环

## 第 1 层：流量守卫

- 程序 `/usr/local/sbin/traffic-guard.py`，由 `traffic-guard.timer` 每 5 分钟触发一次（oneshot service）
- 统计 eth0 出向字节数，状态存 `/var/lib/traffic-guard/state.json`，重启不丢数（网卡计数清零时自动折进 offset）
- 到 780GB（stage 1）：停 Hysteria2 与 WireGuard，网站照常
- 到 790GB（stage 2）：再经专用 iptables 链 TRAFFIC_GUARD 封全部对外，只放行 lo 与 SSH（tcp/22 回包）
- 到新周期第一天：自动解封、重启 VPN、计数清零

## 第 2 层：fail2ban

- 配置 `/etc/fail2ban/jail.d/sshd-ken.conf`，只开 sshd 一个 jail，backend 走 systemd 日志
- 规则：10 分钟内失败 5 次封 24 小时；重复被封时长翻倍，最长 1 周
- 白名单：本机回环 + 服务器自身公网 IP
- SSH 密码登录保持开启（手机救急口），本脚本不动 sshd 配置；root 一律只认密钥
- 注意：自己用密码登录时 10 分钟内连输错 5 次也会被封当前 IP 24 小时，找 Muse 用密钥解封，或在服务器上执行 `fail2ban-client set sshd unbanip <IP>`
- 现行机实测（2026-11-10）：装机当天正值爆破高峰约 615 次失败/小时，装后 3 小时降到 68 次、次日降到个位数/小时

## 第 3 层：每日检测看门狗（Muse 侧）

不在服务器上，是 Muse 的定时任务 `sg-server-daily-check`，每天约 09:42（Asia/Shanghai）只读巡检现行服务器（128.1.x.x）：

- 检查项：服务存活（HY2 / jpcard / nginx / sub 等）、SSH 登录核主机密钥指纹（与标准备份比对，平台换钥时按已批准例外自动还原并报告）、SSH 失败统计（24 小时总量或单 IP ≥100 次报警）、VPN 接入 IP（24 小时不同 IP 超 3 个报警）、负载 / 内存 / swap / OOM、流量守卫读数（超 700GB 报警）、磁盘超 85%、word 与 eg 两个站点公网 200
- 原则：只报不处置；全部正常时静默，不发任何消息
- 有异常：报主对话，并经微信（ClawBot 桥）全文再发一份；微信令牌窗口过期或网关故障时跳过微信、主对话照常
- 状态文件：Muse 工作区 goals/overseas-vps-purchase-for-ai-access-and-website-hosting/hidden_files/server-daily-check-state.json（已知 IP 与密钥指纹清单在里面）

换新服务器后要做的：把巡检目标换成新机地址与新主机密钥指纹、重建已知 IP 清单，其余规格不变。
